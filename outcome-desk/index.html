3. Routing

Autopilot, Copilot, or a person

Casap's public site describes two modes: Autopilot, where the agent acts on its own, and Copilot, where a person approves before anything goes out.

This plan adds a third lane, accounts the agent does not act on at all, and routes every account in the queue by the credit union's written policy. Each account carries the rule ids that decided its lane.

The written policy

These rules are the synthetic credit union's own written collections policy. They are an example of an institution's policy, not a statement of what any law or regulation requires.

Hard exclusions win over everything else. Counts show the accounts each rule decided; one account can be decided by more than one rule.

    5. Governance

    Governance pack

    What a compliance officer, a model governance reviewer, or an examiner would ask for: the record of every agent action, how a policy change is controlled, and where each answer sits on this page.

    Audit log, simulated pilot

      Questions an examiner would ask

      1. Why did the agent contact this member? Account lookup shows the lane and the rule ids; the audit log shows the template and the time.
      2. Which accounts can the agent never act on, and how do you know none were contacted? The written policy, rules P-01 to P-07, and checks C06 and C14.
      3. Who approved each Copilot message? The approver column in the audit log.
      4. How was the pilot judged, and were the stop rules set before the results? Pilot design and the readout.
      5. What happens when the policy changes? Change control lists every account that moves and requires a named approver.
      6. How do you know the figures are right? Checks and the method note.
      7. Did a model write any of the explanations a member or examiner sees here? No. See the method note.

      7. Playbook

      What repeats

      The parts of this plan that carry to the next queue, the next credit union, or the next use case: disputes, fraud, claims or onboarding.

      Data request list

        Who to sit with in week one

        • Operations: the collections manager and two collectors, to watch the work and run the time study.
        • Fraud and disputes: the person who receives dispute hand-offs, to agree what the agent must never touch.
        • Executive: the sponsor who owns the cure-rate number, to agree the success metric and the stop rules in writing.
        • Compliance: to read the routing policy line by line before any account is routed.

        Sizing steps

        1. Baseline the queue by bucket: accounts, balances, cure rate from history.
        2. Time the work by task for one month. Hours times a stated loaded rate gives dollars.
        3. For each candidate use, count the hours in scope and the accounts where a wrong automated action would break policy.
        4. Write any outcome gain as a low, base and high assumption, and name the pilot that will test it.
        5. Rank, then pick one use for the first pilot.

        Routing policy template

        1. Hard exclusions first: each a flag, a rule id, and the lane a person.
        2. Copilot triggers next: each a field, a test and a threshold the institution writes down.
        3. Autopilot only when no rule hits, under its own rule id.
        4. Every account gets a lane and the rule ids that decided it. Every change to a rule has an approver and a list of accounts it moves.

        Pilot template

        1. Population from the routing policy, never hand-picked.
        2. Holdout drawn by a seeded hash, so anyone can redraw it.
        3. One success metric and its window.
        4. Smallest detectable effect computed before launch and compared with the assumption.
        5. Guardrails with stop rules, written before the first result.
        6. A decision rule that turns the readout into expand, continue or stop.
        Method

        How this page is made and checked

        Deterministic text only. Every sentence on this page is fixed text written in advance and filled with figures the engine computes. No model writes or computes anything here, and the page makes no network request.

        One engine. engine.js computes every figure from the synthetic data embedded in the page, in your browser, and the same file runs in Node for the publish gate.

        A second implementation. golden.py, written in Python from the same specification with exact fraction arithmetic, computed the goldens embedded in the page. The checks compare the two to the cent, and to 1e-9 on the pilot statistics.

        The publish gate. check.mjs refuses to publish if any figure disagrees with the golden, if any excluded account is on Autopilot, if any agent action breaks the policy, or if the page has an em dash, an en dash, an exclamation point, an external resource, or no noindex tag.

        Mutations. mutate.mjs plants mistakes in the rules, the data and the page, one at a time, and confirms the gate stops each one.

        What this does not show. No real member data, no real credit union, and no deployment: nobody uses this. The cure-rate gains are assumptions. The pilot readout is simulated from outcomes generated with a known effect.
